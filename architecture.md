# Архитектура Eco.Lab1: задание № 76

## Назначение и статус

Цель — ACOM-компонент, который минимизирует пользовательскую функцию потерь по многомерному вектору весов методом градиентного спуска. Клиент передаёт функцию потерь, шаг обучения и начальные веса. Это задание раздела 7, категория 9–10 баллов (`docs/Список заданий_1_v1.pdf`, стр. 7). Общая постановка требует собственного интерфейса, для сложных задач — собственного интерфейса данных, работающего консольного UnitTest, сборки, отчёта по точности и производительности.

Сейчас `Eco.Lab1` сохраняет старый `IEcoLab1::MyFunction` и единственную фабрику, а также реализует `IEcoArtificialIntelligence`, `IEcoVector` и необязательный `IEcoOptimizationTrace`. Консольный UnitTest проверяет численные и ABI-сценарии; нативная сборка Apple Clang запускается на macOS arm64. `Eco.Framework` предоставляет публичные интерфейсы и двоичные компоненты, но не реализацию вектора задачи. `Eco.AI.Promts` остаётся справочным материалом, а не исполняемой зависимостью. В `docs/EcoLab1.pdf` и `docs/ekornev_report_lab3.pdf` разобраны сортировки, их код не переносится в оптимизатор.

## Границы компонентов

| Часть | Ответственность | Граница |
| --- | --- | --- |
| Консольный клиент в `UnitTestFiles` | Создать веса и callback потерь, запросить компонент, проверить результаты и измерить время | Не вычисляет градиент вместо компонента |
| Публичный интерфейс оптимизатора `IEcoArtificialIntelligence` | Создать вектор, принять веса, callback и параметры шага; вернуть новый вектор, статус и диагностические значения | ABI и владение данными закреплены в OpenSpec |
| Публичный интерфейс наблюдения `IEcoOptimizationTrace` | Вызвать тот же оптимизатор со снимками начальных и полностью обновлённых весов | Отдельный IID; старый `Optimize` не меняется |
| Публичный интерфейс данных `IEcoVector` | Представить размер и элементы вектора `double_t` с явным владением и проверкой границ | Не зависит от конкретной функции потерь |
| Реализация `CEcoLab1` и фабрика | Получить нужные службы ACOM, выполнить итерации, управлять временной памятью и ссылками | Не вызывает libc и не зависит от конкретной модели или MSE |
| `Eco.Framework` | `IEcoUnknown`, интерфейсная шина, системный интерфейс, аллокатор и при необходимости сервисы вывода/времени | Готовые компоненты не изменяются ради лабораторной |
| `Eco.AI.Promts` | Примеры IDL, фабрики, ACOM-именования и C89-оформления | Шаблоны требуют адаптации и проверки; код из них не подключается как библиотека |

Компонент `Eco.Lab1` остаётся точкой регистрации с текущим `CID_EcoLab1` и одной зарегистрированной фабрикой; объект вектора создаётся через метод компонента и отдельной регистрации не требует. Новые интерфейсы имеют собственные IID. Опубликованный `IEcoLab1` и порядок его методов, как и уже опубликованный `IEcoArtificialIntelligence`, не меняются: расширение выполняется новым интерфейсом, а не изменением VTbl. Точки подключения, агрегация и включение калькуляторов для задачи № 76 не требуются.

Интерфейс вектора нужен именно для весов задачи № 76. Общая постановка упоминает также матрицы и комплексные числа для сложных задач, но их роль в № 76 не уточняет. Достаточность векторного интерфейса обоснована в OpenSpec; остальные типы добавляются только при подтверждённой потребности. Базовые арифметические компоненты из общей постановки не являются зависимостью оптимизатора.

## Действующий контракт оптимизации

- `IEcoArtificialIntelligence` предоставляет создание `IEcoVector` и сервисный, не сохраняющий состояние модели вызов оптимизации. Вектор поддерживает получение размера, чтение и запись элемента; клиент владеет полученным интерфейсом. Клиент передаёт в `Optimize` входной вектор и контекст callback, а при успехе получает новый вектор результата с собственной ссылкой. Закреплённый callback имеет тип `int16_t (ECOCALLMETHOD *)(const double_t* weights, uint32_t count, voidptr_t context, double_t* outLoss)`. Он получает доступный только на время вызова массив пробных весов, возвращает статус и значение потерь; данные обучающей выборки находятся в контексте клиента.
- Параметры включают положительный конечный шаг обучения, предел числа итераций, шаг численного дифференцирования и критерий остановки. Последние три параметра — проектное решение, обоснованное в спецификации и отчёте.
- При наличии только значения функции потерь градиент вычисляется центральными разностями: `g[i] = (L(w + h_i e_i) - L(w - h_i e_i)) / (2 h_i)`. Для каждого измерения используются независимые пробные веса; все `g[i]` относятся к одной исходной точке. Затем одновременно вычисляются `w_next[i] = w[i] - learning_rate * g[i]`. Для `n` весов требуется ровно `2n` вызовов функции потерь на проверку градиента и ещё один финальный вызов; рабочая память — `O(n)`.
- Все итерации выполняются на рабочей копии. Входной вектор клиента не меняется; новый выходной интерфейс публикуется только после успешного завершения всего вызова. Ошибка callback, выделения памяти, нечисловое/бесконечное значение, переполнение вычисления или некорректные параметры не оставляют частичный результат. При достижении предела итераций возвращаются успешный статус, достигнутые веса и `outConverged = 0`.
- `IEcoOptimizationTrace` вызывает `EcoIterationObserver` с начальными весами и после каждого полного обновления. Это необязательная событийная визуализация без хранения истории и без изменения старого ABI; её контракт закреплён отдельным OpenSpec change.
- Callback вызывается синхронно. Пробный вектор принадлежит оптимизатору и действителен только во время вызова; callback не должен его менять или сохранять. Один экземпляр компонента не обязан обслуживать параллельные вызовы: в текущей конфигурации `threadSafe` выключен.

Поток данных: клиент → `QueryComponent`/`QueryInterface` → проверка входов → копия весов и рабочие векторы через `IEcoMemoryAllocator1` → вызовы функции потерь → полный градиент → обновление рабочей копии → проверка остановки → создание выходного `IEcoVector` → результат клиенту. На всех ветках завершения временная память и полученные интерфейсы освобождаются.

## Привязка к текущему дереву

- `SharedFiles`: IDL и согласованные C-заголовки трёх новых интерфейсов, идентификаторы и коды ошибок. Опубликованные `IEcoLab1.h`/`IdEcoLab1.h` сохранены.
- `HeaderFiles`: внутреннее состояние оптимизатора и объекта вектора.
- `SourceFiles`: численный алгоритм, вектор и единственная фабрика.
- `UnitTestFiles`: консольные сценарии для квадратичной функции, MSE, наблюдения траектории и ошибочных/краевых входов; тест сравнивает веса и значение потерь с независимым эталоном. Отдельный C89-клиент получает снимки через `OptimizeObserved` и готовит таблицу с ASCII-графиком для размерностей 1, 2, 5 и 10; многомерные снимки проверяются по аналитической рекурсии.
- `AssemblyFiles`: сборочные проекты и нативные скрипты Apple Clang для UnitTest и терминальной демонстрации. Linux Makefile, Xcode-проекты и воспроизводимые macOS-скрипты задают C89. На этой машине `xcodebuild` без полного Xcode не работает, а Linux GCC/Make в `toolchain` являются ELF x86-64.
- `DesignFiles`: Word-отчёт по шести адаптированным разделам, исходник отчёта и журнал фактических проверок; прежние FODT-файлы остаются черновиками генератора и не описывают задание № 76.

## Критерии итоговой реализации

Корректность проверяется на задачах с известным минимумом и разных размерностях, на другом callback без изменения компонента, на нулевой размерности, плохом шаге, ошибке callback, нечисловых значениях и повторных вызовах. Для сравнения точности записываются одинаковые начальные веса, критерии остановки и допуск; для скорости — одна и та же функция потерь, размерность, число итераций и платформа. В C нет стандартного аналога многомерного оптимизатора в `math.h`, поэтому эталоном может быть независимая реализация формул или MATLAB; выбранный эталон должен быть описан в отчёте. Сравнительный код не становится зависимостью компонента.

Дополнительные баллы за документирование промта и одновременную сервисную/объектную архитектуру перечислены в задании отдельно. `Eco.AI.Promts` может быть исходным материалом для раздела отчёта об инжиниринге промптов, но сама папка не заменяет финальный использованный промпт, историю исправлений и проверенный пример кода, требуемые постановкой. Эти направления не входят в базовый объём реализации № 76, пока пользователь не выберет их.
