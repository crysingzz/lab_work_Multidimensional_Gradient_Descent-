# Design

## Context

См. [proposal.md](proposal.md) и [specs/optimization-trace/spec.md](specs/optimization-trace/spec.md). Текущий оптимизатор имеет одну фабрику, два представления общего объекта, сервисный метод `Optimize` и отдельный `IEcoVector`. Образец `docs/EcoLab1.pdf` показывает структуру отчёта по быстрой сортировке; его включение калькуляторов и события сортировки не являются требованиями к заданию № 76.

## Goals / Non-Goals

**Goals:** получить наблюдаемую последовательность реальных весов без дополнительного вычисления потери, сохранить старый ABI и ресурсную семантику, проверить траекторию на аналитически известной задаче.

**Non-Goals:** второй оптимизатор, графический GUI, калькуляторы A/B/D/E, хранение истории в компоненте, гарантия сходимости произвольной функции.

## Decisions

### 1. Новый IID вместо добавления метода к старому

`IEcoOptimizationTrace` получает IID `{1C56BC65-1759-4278-80AF-4EDD861B2720}` (сверен поиском по публичным файлам; совпадений нет). Сначала создаётся IDL, затем C-заголовок. Третье представление хранит указатель на тот же объект и общий счётчик ссылок. `QueryInterface` из него возвращает оба прежних IID и канонический `IEcoUnknown`. Альтернатива — расширить старую VTbl — разрушила бы опубликованный ABI; отдельная фабрика нарушила бы требование одной регистрации.

### 2. Один численный путь

Оба публичных метода вызывают общий внутренний расчёт, который принимает необязательный callback observer. Старый `Optimize` передаёт `NULL`, новый `OptimizeObserved` требует ненулевой callback. Начальный снимок выдаётся после валидации и чтения всех весов; последующие — только после копирования полного обновлённого вектора. Это делает порядок определённым и исключает частичные покоординатные снимки. Сообщение о сходимости остаётся в существующем `outConverged`, а не добавляется в событие. Альтернатива — callback на каждую пробную точку — смешала бы наблюдение за весами с `2n` вычислениями потери.

### 3. Ошибка callback

Любой ненулевой статус observer прерывает метод через общую очистку. Выходные диагностики публикуются только после финального успешного вычисления потери и создания нового вектора. Компонент не может откатить внешние действия клиента, который уже получил снимки; это прямо указано в контракте. Альтернатива — игнорировать статус — скрыла бы сбой визуализатора.

### 4. Этапы отчёта

Теория описывает `k` проверок градиента и `n` весов: `2nk+1` вызовов потери, а так как каждая проба копирует `n` весов, время `O(k(n²+n·C_loss)+n)`, память `O(n)`. Улучшения отделяют уже реализованные численные меры от гипотетических методов; не утверждают ускорение без измерений. Раздел поддержки компонентов показывает только реально проверенные Eco System, InterfaceBus, MemoryAllocator и маршруты `QueryInterface`. Раздел визуализации приводит снимки траектории из теста и их смысл, не обещая графическое окно. Для графика или таблиц можно использовать клиентскую обработку записанных результатов, не добавляя libc в реализацию компонента.

## Risks / Trade-offs

- [Observer может быть дорогим] → путь без него остаётся прежним; замеры базовой скорости не смешивать с наблюдением.
- [Обратный вызов изменяет собственный контекст или имеет внешние побочные эффекты] → документировать только синхронное заимствование и отсутствие отката внешних эффектов.
- [Не удаётся получить печатную трассу без запрещённого libc] → хранить и проверять снимки в консольном UnitTest; визуализацию в отчёте строить только из фактических проверенных данных.
- [Word-рендерер на машине недоступен] → запускать положенную проверку, фиксировать точную ошибку и доступную альтернативную визуальную проверку, не объявляя непроверенную пагинацию.

## Migration Plan

Старый клиент не меняется. Новый клиент запрашивает третий IID и освобождает его по `Release`. При откате удаляются новый IDL/заголовок и представление; старые IIDs и CID остаются прежними.
